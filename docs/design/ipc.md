# System calls and IPC

This note describes how programs talk to Radix and to each other as of
Phase 5: user mode and the system call entry, the twelve system calls and
the capability methods behind `cap_call`, the interface definitions in
`abi/*.ridl` and what `ridlc` makes of them, endpoints, notifications,
shared-memory channels, rings, the random capability, how the kernel
starts the user-mode test programs, and how the benchmarks measure all of
it. It ends with the semi-formal argument that the IPC mechanism is
correct and the checks behind it. The user-facing overview is
`radix-ipc(7)`; each system call and interface has its own page in
section 2, generated from the same files the code is. The decisions behind
the design are ADRs 0031 to 0036.

## User mode

Each program runs in an address space of its own. The lower half from
`USER_START` (0x10000) to `USER_TOP` (one page below the end of the lower
half) is the program's; the pages below `USER_START` stay unmapped so that
null pointers fault, and the last page stays unmapped so that no
`syscall` instruction can sit at the very end of the half, where `sysretq`
would return to a non-canonical address. The kernel's half is mapped
supervisor-only in every address space, as in Phase 2.

**Entry and exit.** A program enters the kernel with `syscall`. FMASK
clears IF, TF, DF, AC, IOPL and NT, so the kernel always starts with
interrupts off and SMAP in force. The entry stub swaps GS to the CPU's
data, parks the program's stack pointer, switches to the running thread's
kernel stack (stored in the CPU's data at every context switch) and pushes
every register as a `SyscallFrame`. The handler enables interrupts once
on the kernel stack, so a long system call can be preempted like any
kernel code. On the way out the stub restores every register from the
frame, so nothing of the kernel's leaks into the program, and leaves with
`sysretq`. Before that the kernel checks that the return address is a
user address, since Intel CPUs fault in kernel mode, on the program's
stack, when SYSRET's target is non-canonical, and that the flags are ones
a program may hold. Interrupts and exceptions from user mode reach the
same kernel stack through the TSS; their stub swaps GS when the saved CS
is the user's.

**AMD's SYSRET.** STAR's user selector base carries privilege level 3
(`USER_BASE` is 0x1b), so the stack selector SYSRET loads is 0x23. Intel
CPUs force the low bits of SS to 3 whatever STAR says, and QEMU's
emulator does too, but AMD CPUs load them as written: with a base of
0x18, a program ran with SS 0x20, and the first `iretq` back to it (after
an interrupt) raised a general protection fault on that selector. CI's
runners are a mix of Intel and AMD machines, which is why the benchmark
boot failed only some of the time. AMD CPUs also keep SS's hidden
attributes from before a SYSRET, so a thread switched in after one may
run kernel code with an SS that is not quite the kernel's; the context
switch reloads SS with the kernel's selector when it differs, as Linux
does for the same erratum (`X86_BUG_SYSRET_SS_ATTRS`).

**Faults.** An exception in user mode never reaches the kernel's panic
path: the architecture hands it to the kernel's user fault handler, which
logs it (`User: thread 9 (fault) ended: page fault writing 0x10000 (not
allowed) at pc 0x401b51, sp 0x7feffffffed0`) and ends the thread with
status `EXIT_FAULT`. The breakpoint gate has DPL 3, so a program's `int3`
is a breakpoint and not a protection fault.

**User copies.** The kernel reads and writes user memory only through
`copy_from_user` and `copy_to_user`. Each checks that the range lies in
the user half (`radix_ipc::range`, proved with Kani), lifts SMAP with
`stac` for one `rep movsb` and puts it back with `clac`. A page fault on
that instruction does not panic: the fault handler moves the instruction
pointer to the end of the copy (`fixup`) and the copy reports failure,
which becomes `bad_address`. Memory the kernel shares with a program for
a longer time, such as a ring's pages, is allocated by the kernel, kept
mapped in its own half and read and written there with volatile accesses
(`Shared`), never through the program's mapping.

**Status words.** Every system call returns a status in `rax`: 0 for
success, otherwise `(detail << 32) | (domain << 16) | code`. Domain 1 is
the kernel, whose codes are listed in `radix-errors(2)` with the errno
each maps to; the detail says more where it can (the rights missing, the
kind found). Later phases give other domains to services.

## The twelve system calls and capability methods

Radix has twelve system calls. Arguments and results travel in ten
registers (`rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`, `r12`, `r13`, `r14`,
`r15`), so a message of eight words fits next to a capability and an info
word, both ways, without touching memory:

| Number | Call | What it does |
| --- | --- | --- |
| 0 | `cap_call` | Calls an endpoint (send, then wait for the reply), or a method of any other object |
| 1 | `send` | Sends a message on an endpoint |
| 2 | `recv` | Receives a message from an endpoint |
| 3 | `reply_recv` | Replies to the last caller, then receives |
| 4 | `notify` | Signals a notification |
| 5 | `wait` | Waits for a notification, with a timeout or as a poll |
| 6 | `yield` | Gives the CPU to another ready thread |
| 7 | `map` | Maps pages of a frame into an address space |
| 8 | `unmap` | Unmaps pages from an address space |
| 9 | `ring_setup` | Makes a ring and maps its shared pages |
| 10 | `ring_enter` | Submits ring entries and waits for completions |
| 11 | `debug_log` | Writes a line to the kernel log |

Everything else is a *method* of an object, called with `cap_call` on its
capability: the label of the info word is `(interface << 16) | method`, and
arguments and results are the message's words. The methods of
`radix-capability(2)` (interface 0xffff: info, derive, move_to, delete,
revoke, seal, unseal) work on every capability; labels from 0xffff0000 up
are kept for them, so an endpoint's own protocol can never collide with
them. The others work on the kind their interface is for: retyping
memory into frames (`radix-memory(2)`), frame and address-space queries,
a thread's thread pointer and exit (`radix-thread(2)`), random bytes
(`radix-random(2)`) and ring information (`radix-ring(2)`). A label that
is no method of the object's interface fails with `no_such_method`.

Every capability lookup goes through the capability store of Phase 3 and
the object registry (`user/objects.rs`), which maps the store's object
names to the kernel objects behind them and is told when the store
releases a name, so the object closes when its last capability goes: an
endpoint fails its waiters with `gone`, a frame is unmapped from every
address space. Phase 5 adds three object kinds to the store's twelve:
`random`, `ring` and `kernel_log`.

## Interface definitions: ridl and ridlc

The system calls, interfaces, errors and shared layouts are written down
once, in `abi/*.ridl`, one module per file. `ridlc` parses them, checks
them and writes three outputs:

- Rust (`radix-abi`, from its build script): an argument and a result
  struct per call and method, with `decode` and `encode` for the kernel
  (decoding checks every argument, so the kernel never sees an invalid
  enum value or flag), wrappers generic over a `Syscalls` trait for
  programs, and `#[repr(C)]` structures with their sizes checked;
- C headers (`out/sysroot/system/include/radix/`, written by `ob build`), with
  `static inline` wrappers around the system call instruction;
- man(2) pages in scdoc (`out/docs/man-src/`, built by `ob docs`), one per
  system call with its registers and errors, one per module.

The checks refuse what would break the interface rather than warn:
every item, member and parameter needs documentation; numbers and names
are unique; a call's arguments and results fit the ten registers; a
structure has no hidden padding; every error a call raises exists. The
language is small on purpose: primitive integers, slots, addresses,
fixed arrays, flags, enums, structures, and byte buffers passed by
address and length (`in bytes`, `out bytes`), which the kernel copies with
the user-copy primitives.

## Endpoints

An endpoint carries synchronous messages, after the L4 family and seL4. A
message is an info word and up to eight data words:

| Bits of the info word | Meaning |
| --- | --- |
| 0 to 31 | The label: whatever the protocol says, or a method number |
| 32 to 35 | How many data words carry meaning (0 to 8) |
| 36 to 38 | How many capabilities the message carries (0 to 4) |
| 40 | Move the capabilities instead of copying them |
| 41 | Do not block: fail with `would_block` instead of waiting |

The kernel copies the words from the sender's saved registers straight
into the receiver's: a register-only message never touches memory and
never takes the capability store's lock. Whichever of sender and receiver
comes second hands the message over under the endpoint's lock and wakes
the other; the first waits in the endpoint's queue of senders or
receivers, first come first served. The receiver gets the sender's badge,
so a server tells its clients apart by the badges it gave them.

A *call* (`cap_call` on an endpoint) sends and then waits for the reply.
The receiver of the call holds the caller until it replies (`reply_recv`)
and only it can reply; if it receives again without replying, or exits,
the caller gets `gone`. The caller's IPC state, under its own lock, says
whether it still waits for a reply, which settles the races between a
reply, a server letting go of its caller, and the caller being stopped.

**The fast path.** When a message or a reply wakes the other side, the
kernel uses `sched::wake_sync`: a woken thread that may run on this CPU is
queued here, where it runs as soon as the waker blocks, instead of on
another CPU that would need an interrupt. A call and its reply between
two threads on one CPU are then two system calls and two switches, with no
interrupt.

**Capabilities in messages.** A message carries up to four capabilities,
named by its first data words, when the sender's endpoint capability has
the `grant` right. Under the store's lock they are copied (with the
source's `copy` right) or moved into the first empty slots of the
receiver's *receive window*, a range of slots each thread sets, and the
receiver finds those slot numbers in place of the sender's. The transfer
is all or nothing. A copy across capability spaces needs the `transfer`
right too (ADR 0023). A reply to a call may carry capabilities when the
call came through a capability with `grant`.

**Lock order.** The capability store, then an endpoint, then a thread's
IPC state; never two of a kind. A receiver that sees a queued sender with
capabilities retries with the store's lock taken first. No lock is held
while a thread blocks.

## Notifications

A notification is a word of bits, after seL4's. `notify` sets the bits of
the capability's badge (bit 0 when it has none) and wakes the waiters;
`wait` takes the whole word and leaves 0, sleeping while it is 0. Signals
that arrive while nobody waits add up in the word, so none is lost, but
several of the same bit are one. A ring can wait for a notification
without blocking a thread (the `wait` ring operation), and a signal goes
to a waiting ring before the word.

## Shared-memory channels

Channels are built from the pieces above, entirely in `libradix`: two
programs map the same 4 KiB frame, which holds two single-producer,
single-consumer queues of sixteen 64-byte messages, one each way, and
each program has a notification to sleep on. The messages never pass
through the kernel, and an end that never has to wait makes no system
call at all (ADR 0038):

- Each queue has a reader's word beside its head and a writer's word
  beside its tail, each on the cache line its owner writes anyway.
- An end that finds its queue empty (to receive) or full (to send) sets
  its word on that queue, looks at the indexes again, and only then waits
  on its notification, which keeps a signal that came first; it clears
  the word once it is done.
- After writing a message (moving the tail), a writer signals the
  reader's notification only if the reader's word is set; after reading
  one (moving the head), a reader signals the writer only if the
  writer's word is set.
- The word's store and the second look, and the index's store and the
  word's load, are sequentially consistent: either the waiter sees the
  index move, or the other end sees the word and signals. This is the
  pattern of Linux's futexes.

A round trip on one CPU therefore takes two context switches. The TLA+
model `userspace/libradix/tla/Channel.tla` checks the protocol with
one-message queues, for ping-pong, bursts that fill the queue and both
ends sending first: no deadlock, and both ends always finish (about
4,900 states).

## Rings

`radix-ring`, after Linux's io_uring, batches many operations into one
system call. `ring_setup` makes a ring of 2ⁿ submission entries (up to
4,096) and twice as many completion entries; the kernel allocates the
pages, charges them to the creating thread's resource domain, keeps them
mapped in its own half and maps them read-write into the program. The
header (`RingHeader`) gives the queues' indexes, each on a cache line of
its own, and the offsets of the entries.

`ring_enter` takes up to `submit` new entries, carries them out and waits
until `min_complete` completions are waiting. The kernel keeps its own
submission head and completion tail and masks every index the program
wrote; it takes an entry only after reserving room for its completion
(`radix_ipc::ring::Queues`), so nothing the program writes makes the
kernel write outside the ring or lose a completion. A full completion
queue stops submission: `ring_enter` takes nothing more, and fails with
`busy` if it took nothing at all. A submission tail more than a queue's
length ahead of the kernel's head is an `invalid_argument`. Entries are
copied out of shared memory once, in batches of 16 under the ring's lock,
carried out without it, and completed under it again, the completion
written before its tail is published with release ordering. A waiter
counts itself in the ring's `waiting` before it looks at the tail, and
whoever publishes a completion looks at `waiting` before it wakes
anyone; a full barrier on each side, between the write and the read,
makes sure that one of them sees the other. Until Phase 8 neither side
had one, and on x86 a store can wait in the store buffer while a later
load goes ahead, so a ring round trip between two CPUs could lose a
wake-up and hang; `ob bench` on a CI runner found it.

The operations are `nop`, `notify`, `wait` (completes when a notification
is signalled), `msg_ring` (posts a completion to another ring, the
ring-to-ring message the `ring` pair of the self-tests ping-pongs with),
`random` (16 random bytes) and `timeout`. Later phases add I/O.

## The random capability

Every program receives a capability to the kernel's random number
generator (Phase 2, `docs/design/random.md`) in slot 4 at start. Its
`read` method fills a buffer of up to 64 KiB (`READ_MAX`), copied out 256
bytes at a time so no large buffer is held on the kernel stack, and
`words` returns 64 bytes in registers without touching memory, which is
what address-space randomisation, stack canaries and hash seeds need at
start.

## Starting the test programs

The kernel starts the user-mode test programs from one statically linked
ELF64 image that GRUB loads as a module named `usertests` (ADR 0036). A
`Group` (`user/launch.rs`) starts programs from it and waits for them;
since Phase 6 each is a process of its own, loaded by the kernel's
loader as Spark is (`docs/design/processes.md`): a capability space of
256 slots, an address space with the image's segments, a 256 KiB stack
below `STACK_TOP`, a read-only start-up page at 0x10000
(`radix-startup(2)`), and one thread pinned to the CPU asked for, which
starts at the entry point with the start-up page's address as its
argument. The image stays a fixed executable, linked at 0x400000, so
that its addresses are the same in every run. The start-up page names
the program's *role*: the image holds every test program, and the role
says which one this is. The frames come from the program's own memory
object, but their capabilities are kept with its process so a program
cannot unmap its own code by deleting a capability. When the group ends,
every process goes, and with it everything the programs had; the `user`,
`ipc` and `fuzz` self-tests check that the capability store and the
object registry hold what they held before the first program started.

The `usertests` programs (`userspace/usertests`) are:

- the probe, which calls every system call and method with good and bad
  arguments and checks each answer, and writes lines with control
  characters, bad UTF-8 and too many bytes, whose escaping and cut the
  `user` boot test checks in the kernel log;
- the fault program, which makes one of eight faults;
- five pairs: `call`/`echo` over an endpoint, `cap_send`/`cap_receive`
  passing capabilities, `notify_ping`/`notify_pong`, `channel_a`/
  `channel_b` and `ring_a`/`ring_b`;
- the system call benchmark.

## Benchmarks

`ob bench` boots a test image with `selftest=bench` on 2 CPUs and reads
the `BENCH` lines the programs log. Then it boots Linux in a virtual
machine set up the same way (q35, 2 CPUs, 1 GiB, KVM, `-cpu host`), with
a static `tools/linux-bench` as its only process, for the closest Linux
operations, and runs `linux-bench` on the host too, for reference
(ADR 0039). The Linux in the virtual machine is the runner's own kernel,
booted with `mitigations=off`, since Radix has no mitigations of CPU
vulnerabilities yet. The method follows lmbench's `lat_syscall`,
`lat_ctx`, `lat_pipe` and `lat_unix`:

- each measurement times a loop of many operations (200,000 system calls,
  100,000 round trips) with the TSC, read with `lfence; rdtsc` before and
  after, and divides by the count, so the cost of reading the clock
  disappears; the kernel gives the TSC's frequency in the start-up page;
- a round trip is one message there and back between two programs, both
  pinned to one CPU or to two;
- on Linux, the same with two threads (or processes) pinned with
  `sched_setaffinity`, and `std::time::Instant` around the loop.

| Radix | Linux baseline |
| --- | --- |
| `syscall_null`: an unknown system call number, which only enters and leaves the kernel | `getppid` through `syscall(2)` |
| `syscall_yield`: `yield` with nothing else to run | `sched_yield` |
| `cap_info`: the `info` method of a capability | `fcntl(F_GETFD)`: a look-up in the file table |
| `random_words`: 64 random bytes in registers | `getrandom`, 64 bytes |
| `context_switch`: two programs on one CPU yielding to each other, per switch the kernel counts | two processes calling `sched_yield`, per switch `getrusage` counts |
| `fresh_page`: a page made from memory, mapped, written, unmapped and given back | `mmap`, a first-touch fault, `munmap` |
| `tlb_local`: a page mapped and unmapped in an address space no other CPU runs | `mprotect` to none and back, with no other thread |
| `tlb_shootdown`: a page mapped and unmapped while the address space runs on the other CPU | `mprotect` to none and back while a thread spins on the other CPU |
| `memory_copy`: `rep movsb` between two 32 MiB buffers, per MiB, in the fastest of 5 batches of 6 copies | the same copy, the same way |
| `endpoint_call_*`: `cap_call` answered with `reply_recv` | a pipe round trip |
| `notification_pingpong_*`: `notify` and `wait` each way | an eventfd round trip |
| `channel_roundtrip_*`: a message each way through a channel | a futex ping-pong |
| `ring_roundtrip_*`: `msg_ring` each way between two rings | a Unix socket round trip |
| `syscall_null_parallel`, `cap_info_parallel`, `random_words_parallel`: the same on both CPUs at once | `getppid`, `fcntl` and `getrandom` on two threads |
| `endpoint_call_parallel`: `endpoint_call_same_cpu` on both CPUs at once, each pair with its own endpoint | a pipe round trip, a pair of threads on each CPU at once |
| `file_open_close`, `file_stat`, `file_read_4k`, `file_write_4k`: a file opened by name beneath a directory and closed, its status by name, and 4 KiB read from and written over its first page, on a tmpfs | `openat` and `close`, `fstatat`, `pread` and `pwrite` of 4 KiB, on a tmpfs |
| `posix_*`: the POSIX benchmarks, a C program on mlibc (below) | the same C program on glibc |

The POSIX benchmarks (ADR 0106) are one C program,
`userspace/posix/bench.c`, which Spark runs on Radix in a second boot of
the test image and `linux-bench` runs last on Linux, built from the same
file with the same compiler. It times, with `clock_gettime`, `fork` and
`waitpid` of a child that exits at once (`posix_fork_wait`); `fork`,
`execv` of itself and `waitpid` (`posix_fork_exec_wait`); 256 MiB
through a pipe in 64 KiB writes from a child, both on one CPU, per MiB
(`posix_pipe_mib`); `kill` of itself with a handler for the signal
(`posix_signal`); `poll` on a pipe with data to read (`posix_poll`); and
two threads passing a turn there and back through two semaphores, on
one CPU and on two (`posix_futex_same_cpu`, `posix_futex_cross_cpu`).

A yield switches only when the other program may run first (EEVDF on
both systems), so `context_switch` divides the time by the switches that
happened: on Radix the kernel's count for the benchmark, which includes
starting and stopping the two programs, and on Linux the sum of both
processes' `ru_nvcsw` and `ru_nivcsw`.

`fresh_page` is how a program got a new page before Radix had demand
paging (the page cache came in Phase 7, and anonymous memory filled on
touch in Phase 8): the same work as a first-touch fault (a zeroed page,
mapped), plus giving it back.

The report shows each Radix number, the Linux one from the virtual
machine, their ratio and the host's Linux. Under KVM a system call does
not leave the guest, and a wake-up on another CPU is an interrupt the
host delivers on both systems alike, so the ratio compares the kernels.
Under KVM, `ob bench` boots Radix and the Linux virtual machine three
times in turn and keeps each row's fastest run on each side (ADR 0046):
the host only ever adds time, and rarely to the same row in every run.
`ob bench --gate` fails if a row is missing or Radix takes longer than
Linux in the virtual machine (ADR 0107); while a row is over, it boots
both systems in turn again, up to six more times, each side keeping its
fastest run, so the noise of a run is set aside and a real difference
stays. CI's `bench` job runs
it on every pull request and every merge to main and shows the report in
the job's summary, with the numbers as an artifact (`results.json`).
Without KVM nothing is comparable: the Linux virtual machine does not
run, the report says so, and `--gate` fails.

The report also gives, for each benchmark, what the kernel did per
operation: switches, timer writes, interprocessor interrupts sent, halts
and wake-ups caught while polling. Under a hypervisor each timer write,
interrupt sent and halt is an exit to the host (ADR 0037).

Timings on shared runners vary by a few percent from run to run, so a
hot path that grows a little can pass the gate for a while. `ob bench
--instructions` counts instead (ADR 0045): it boots the same image under
QEMU's instruction counting (`-icount shift=0,align=off`), where each
instruction moves the guest's clock by one nanosecond, so every `BENCH`
line gives the user and kernel instructions an operation took, the same
on every machine. Each operation on one CPU has a budget in
`tools/xtask/src/bench.rs` (what it took when the budget was set, plus
a tenth), and CI's `instructions` job fails when one goes over. A
change that needs more raises the budget in the same pull request and
says why. Operations on two CPUs depend on how QEMU interleaves the
CPUs, so they have no budget.

**Where the time goes.** A system call enters with `syscall`, saves the
registers, finds the running thread with one read of a per-CPU word
without touching its reference count (`sched::running`), and writes its
results straight into the saved registers (ADR 0042). A capability
method looks the capability up in this CPU's cache when the store has
not changed since (`user::objects::find`), so it takes no lock and
writes nothing shared, and CPUs using capabilities at once do not
contend. The same look finds the object the capability names (an
endpoint, say): each entry keeps a weak reference to it beside the
capability, so the cache holds no object alive, and a hit writes only
the object's own reference count, so pairs of programs calling different
endpoints on different CPUs share no lock (`endpoint_call_parallel`).
The caches empty only when something one of them holds goes (ADR 0077),
so opening and closing files leaves them as they are. Random bytes
come from this CPU's generator, a batch of ChaCha20 blocks at a time. A
same-CPU round trip is two context switches and no timer write, and
waking a thread pinned to a CPU, or one whose last CPU is idle, reads no
other CPU's load; a cross-CPU wake-up finds the other CPU polling (ADR
0037) and costs a write instead of an interrupt.
An unmap picks the CPUs to flush from those the firmware lists, not
from every slot of the per-CPU table: until Phase 8 it looked at all
256, which was most of `tlb_local`'s cost.
A TLB shootdown is the same system calls as `tlb_local` plus an
interrupt to the other CPU and its answer; under KVM most of that time
is the host sending and delivering the interrupt, which Linux pays too.
On a busy host the other virtual CPU may be stopped; both kernels then
skip the interrupt and have the hypervisor flush it before it runs
again (paravirtual TLB flush, ADR 0105).
The receiving CPU ends the interrupt before it flushes, so the
initiator's next request is not yet pending when the hypervisor decides
whether to offer paravirtual EOI (ADR 0041).

## Known limits

- Changes to the capability store all take its one lock, and taking
  away a capability or object that some CPU found empties every CPU's
  cache. Programs that change their capabilities all the time on many
  CPUs at once would queue on the store's lock; a per-space store with
  RCU over the slots is the fix if programs show it matters.
- Rings charge their memory to a resource domain, and since Phase 6 so
  do the endpoints, notifications and processes a program makes with
  `process.create`. Queued messages, and the endpoints and notifications
  the self-tests' groups make, come from the kernel heap uncharged,
  bounded by the slots a program has.
- The self-tests' programs are pinned to a CPU each, which the
  benchmarks need; Spark and the programs it starts are placed by the
  scheduler.

## Correctness

The claims, each with the check that backs it:

1. **A system call never runs kernel code with user state, nor returns
   kernel state.** The stub saves and restores every register, the kernel
   starts with interrupts off and SMAP on, and SYSRET only goes to a user
   address, and a failed call leaves 0 in every result register. *(The
   probe's register check, which makes a call with a marker in every
   register and looks at them afterwards; the `user` boot test's faults,
   including a jump into the kernel's half.)*
2. **User memory is touched only where the program can touch it.** Every
   range is checked against the user half before a copy, without
   overflow (Kani `user_bytes_stay_below_the_top`,
   `user_pages_stay_in_the_user_half`; property
   `user_bytes_never_reach_the_kernel_half`), and a fault during a copy
   becomes `bad_address`. *(The probe passes unmapped, kernel and
   wrapping addresses.)*
3. **An info word means what it says.** Encoding and decoding are exact
   inverses on valid words, and invalid ones are refused (Kani
   `info_words_are_exact`; property `decoded_info_words_encode_back`).
4. **Every message reaches one receiver at most, a send that returned
   success reached one, and a reply comes only from the thread that took
   the call, to that call.** (TLA+ `Endpoint.tla`: `AtMostOnce`,
   `Delivered`, `HeldCallsWait`, `OneHolder`.)
5. **A thread is in an endpoint queue exactly when its state says so,
   and every wait ends**: by a message, a reply, `gone` when the endpoint
   closes or the server lets go, or `interrupted` when the thread is
   stopped. (TLA+ `QueuesMatchStates`, `AllFinish` under fair scheduling;
   the `ipc` boot test.)
6. **A capability transfer is all or nothing and never widens rights.**
   It goes through the store's derive and move, whose rights checks are
   proved in Phase 3, and undoes what it did on any failure. *(The
   `cap_send`/`cap_receive` pair: copies, moves, a closed receive
   window, an endpoint capability without the grant right, and a reply
   that moves a capability back.)*
7. **A ring never makes the kernel write outside it or lose a
   completion**, whatever the program writes into the shared indexes
   (Kani `ring_layouts_are_sound`, `ring_completions_never_overflow`;
   property `completions_never_overflow`; the probe's full completion
   queue, `busy` and nonsense indexes).
8. **No signal of a notification is lost** between a signal and a wait
   (a signal leaves at least one bit set: test
   `notifications_always_leave_a_bit`; the `notify` and `channel` pairs,
   a thousand rounds each on one CPU and two).
9. **A program's fault ends that program only.** *(The `user` boot test's
   eight faults.)*
10. **Nothing a program passes harms the kernel, and a failed call says
    only what its documentation says.** Whatever arguments, ring entries
    and shared indexes a program writes, the kernel does not panic, trip
    the lock checker or keep an object afterwards, and a failed call
    returns an error from its `raises` list (for a method, its own or
    `cap_call`'s), with 0 in every result register. *(The `fuzz` boot
    test: eight groups of three programs make 4,000 random calls each,
    sharing endpoints, notifications and memory, and check every failed
    call against the lists `ridlc` generates from `abi/*.ridl`; then the
    capability store must pass its audit and hold what it held before.)*

**The TLA+ model.** `kernel/ipc/tla/Endpoint.tla` models callers that
send or call several times, servers that receive in a loop and either
reply or receive again without replying, threads that may be stopped at
any moment, and an endpoint that may close at any moment. The safety
configuration has two callers, two servers, two messages each, a caller
and a server that may be stopped and an early close (about 600,000
states, 10 seconds); the liveness configuration drops the stoppable server
and closes the endpoint once the callers are done (about 86,000 states).
Seeded bugs (a reply that does not check that its caller still waits, a
cancel that does not check that the sender is still queued, a server that
does not let go of its caller) each make TLC fail. The mapping to the
code:

| Model | Code |
| --- | --- |
| `HandOver` | `hand_over`, under the endpoint's lock |
| `SendWait`, `ReplyWait`, `RecvWait` | `wait`, reading the thread's IPC state under its lock |
| `CancelSend`, `CancelRecv`, `CancelReply` | `cancel`, under the endpoint's lock or the thread's |
| `Abandon`, `ServerExit` (`LetGo`) | `abandon_caller`, from `recv` and `exiting` |
| `Take` | `take`, under the endpoint's lock |
| `Reply` | `reply` and `deliver_reply` |
| `Close`, `Fail` | `Endpoint::close`: the queues under the lock, then `fail` outside it |
| `Stop` | the out-of-memory policy or a group's end asking a thread to stop |

Waking and blocking are not modelled again: a thread whose step is
enabled by its state takes it, which the Scheduler model justifies (no
lost wake-up, every wait ends).
