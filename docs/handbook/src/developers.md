# For developers

These documents live in the repository rather than in this handbook:

- [`CONTRIBUTING.md`](https://github.com/openlinuxsystems/orthros/blob/main/CONTRIBUTING.md):
  how to build and test, and what a change needs before it merges.
- [`CODE_OF_CONDUCT.md`](https://github.com/openlinuxsystems/orthros/blob/main/CODE_OF_CONDUCT.md),
  [`GOVERNANCE.md`](https://github.com/openlinuxsystems/orthros/blob/main/GOVERNANCE.md)
  and [`SECURITY.md`](https://github.com/openlinuxsystems/orthros/blob/main/SECURITY.md):
  how people work together, who decides, and how to report a vulnerability.
- [`docs/coding-standard.md`](https://github.com/openlinuxsystems/orthros/blob/main/docs/coding-standard.md):
  rules for Rust code, including where `unsafe` is allowed.
- [`docs/adr/`](https://github.com/openlinuxsystems/orthros/tree/main/docs/adr):
  architecture decision records.
- [`docs/roadmap.md`](https://github.com/openlinuxsystems/orthros/blob/main/docs/roadmap.md):
  the implementation plan, phase by phase.
- [`docs/design/`](https://github.com/openlinuxsystems/orthros/tree/main/docs/design):
  how the kernel works: `boot.md`, `interrupts.md`, `memory.md`,
  `random.md`, `capabilities.md`, `scheduler.md`, `ipc.md`,
  `processes.md`, `storage.md` and `posix.md`.

The kernel's source documentation is generated by rustdoc. The kernel
builds for its own target with `core` compiled from source (ADR 0011), so
rustdoc needs the same flags as `ob build`:

```sh
cargo doc --manifest-path kernel/Cargo.toml --target-dir target/kernel \
    --target kernel/targets/x86_64-radix-kernel.json -Zjson-target-spec \
    -Zbuild-std=core,compiler_builtins,alloc \
    --workspace --exclude radix-arch-aarch64 --no-deps --open
```

The kernel libraries under `kernel/lib/` also build for the host, which is
how `./ob test unit` runs their tests:

```sh
cargo test --manifest-path kernel/Cargo.toml -p radix-acpi
```

The memory manager, `radix-mm`, the capability core, `radix-cap`, the
scheduling policy, `radix-sched`, the arithmetic of IPC, `radix-ipc`, and
the storage libraries' bounds (requests and partitions in `radix-block`,
paths in `radix-vfs`, table entries and long names in `radix-fat`) also
have Kani proof harnesses (ADRs 0019, 0030 and 0032), which
`./ob test kani` checks; they take about ten minutes and need the Kani
release `./ob doctor` names:

```sh
cargo install --locked kani-verifier --version 0.68.0
cargo kani setup
./ob test kani
```

The capability core's derivation tree, retyping and revocation are also
modelled in TLA+ (`kernel/cap/tla/`, ADR 0024), and so are how the
scheduler blocks, wakes and switches threads between CPUs and how an
idle CPU is woken (`kernel/sched/tla/`, ADR 0030), how endpoint calls,
replies, cancellation and closing interact (`kernel/ipc/tla/`,
ADR 0032), how the two ends of a shared-memory channel wake each other
(`userspace/libradix/tla/`), how a FAT volume's clusters change hands
while their data waits to be written back (`kernel/fs/fat/tla/`), and
how futex, `poll`, timer and file-lock waits are woken and how `join`
hands half of some work to another CPU (`kernel/radix/tla/`). `./ob test tla` checks the models with the TLC
model checker in about twelve minutes. It needs Java; `ob` downloads
the pinned TLA+ tools itself:

```sh
sudo apt install default-jre-headless
./ob test tla
```

## User programs and the system call interface

The system calls, the methods of every kind of object and the kernel's
errors are defined once, in `abi/*.ridl` (ADR 0033). `tools/ridlc`
compiles them into the Rust bindings of `radix-abi`, the C headers that
`./ob build` installs under `out/sysroot/system/include/radix/`, and the
section 2 man pages that `./ob docs` builds; `ridlc` also runs on its own:

```sh
cargo run -p ridlc -- abi --c out/include --man out/man2
```

The user programs are a workspace of their own, `userspace/`: `libradix`
(entry, system calls, printing, rings and channels); `radix-rt`, the
runtime of native programs on top of it (a heap, arguments, the boot
archive as a read-only file system, and `spawn` to start other programs,
ADR 0051); Spark, the first program, and `hello`, the test program it
starts (`spark(8)`); and `usertests`, the image of test and benchmark
programs that the kernel's `user`, `ipc`, `fuzz` and `bench` self-tests
start (ADR 0036). `./ob build` builds them with the kernel and writes
Spark and `hello` into the boot archive, `out/sysroot/boot/bootfs`;
`./ob test boot --case spark` boots it, and `--case user`, `--case ipc`
and `--case fuzz` run the test image;
`fuzz` makes random system calls from seeds it logs, and
`fuzz-seed=N` on the kernel command line repeats a run (ADR 0043).
`./ob bench` measures system calls, IPC round trips, context switches,
fresh pages, TLB shootdowns, file operations, memory copies and, with one
C program on both systems, fork, exec, pipes, signals, `poll` and
futexes (ADR 0106) on Radix and the closest operations of Linux in a
virtual machine set up the same way, and writes a report to
`out/bench/report.md` (ADR 0039). It needs KVM, and a Linux
kernel it may read: on Debian, Ubuntu and Mint, copy your own once with
`sudo install -m 644 /boot/vmlinuz-$(uname -r) .cache/vmlinuz` and run
`./ob bench --linux-kernel .cache/vmlinuz`. It measures both systems
three times in turn and keeps each operation's fastest run (ADR 0046).
CI runs it with `--gate` on every pull request and merge, and fails if
Radix is slower than Linux at any operation, after measuring both again,
up to six more times, while one is (ADR 0107).
`./ob bench --instructions` needs neither: it counts the instructions
each operation takes under QEMU, and with `--gate` fails if one on one
CPU goes over its budget in `tools/xtask/src/bench.rs`, as CI does
(ADR 0045). A change that needs more raises the budget in the same
pull request and says why. How it all works is in `docs/design/ipc.md`
and `radix-ipc(7)`.

### Adding a program to the boot archive

Programs are static position-independent executables, placed at a random
address each time they start (ADR 0048), and every one is /system code,
so its dependencies must have permissive licenses. To add one:

1. Make a crate in `userspace/` with a `[[bin]]` target, depending on
   `libradix`, `radix-abi` and `radix-rt`, as `userspace/hello` does, and
   add it to the workspace's `members`.
2. Start it with `#![no_std]`, `#![no_main]` and `radix_rt::entry!(main)`;
   `main` gets the start-up page and returns the exit code. `alloc` works,
   `radix_rt::args()` gives the arguments and `println!` writes to the
   kernel log.
3. Add its path in the archive and its package to `ARCHIVE` in
   `tools/xtask/src/userspace.rs`, and its package to `USER_PROGRAMS` in
   `tools/xtask/src/licenses.rs`, so its crates go into the license
   manifest and `cargo deny` checks them.
4. Boot it as the program Spark starts, with arguments:
   `./ob run --cmdline "-- /system/tests/yourprogram one two"`, or as the
   first program itself with `init=/system/tests/yourprogram`.

`tar tvf out/sysroot/boot/bootfs` lists what the archive holds. How
processes are built, loaded and ended is in `radix-processes(7)` and
`docs/design/processes.md`.

## POSIX programs, ports and Rust's standard library

From Phase 8 on, C and Rust programs written for Unix run on Dukovo
through the C library, mlibc, and Rust's standard library on top of it
(radix-posix(7), ADRs 0068 to 0071). `./ob build` writes a toolchain to
`out/toolchain`: `x86_64-radix-cc` compiles and links C for Dukovo with
the host's Clang, as a static position-independent program unless it is
given `-dynamic` or `-shared`, and `out/toolchain/meson/radix.ini`
describes Dukovo to Meson:

```sh
out/toolchain/bin/x86_64-radix-cc -O2 -o hello hello.c
```

### Porting software

Software from elsewhere is a port: a directory `ports/<name>/` with a
`recipe.toml`, patches applied in name order, and a `build.sh`
(ADR 0069; `ob(1)`, PORTS, lists every field and variable). The recipe
pins the source to a full git commit and names its license, home page,
the ports it needs and the files it puts in the image; `ports/lua` is a
short example. `./ob ports` builds them all, each again only when it
changed. Check the license before starting a port: system programs must
have permissive licenses, and every port's license and notices go into
the image's manifest and CREDITS.md. A change to the upstream code is a
patch with a description of what it changes and why, and goes upstream
when it is of general use.

### Programs on Rust's standard library

Programs that use `std` live in `userspace/programs/`, a Cargo workspace
of their own built for the `x86_64-unknown-radix` target with the
standard library `ob` builds from the pinned toolchain's sources
(ADR 0070). They use the `libc` crate's Radix module, which `ob` checks
against the C library's headers after every build. To add one, make a
crate in that workspace, add it to `STD_ARCHIVE` in
`tools/xtask/src/userspace.rs` with its place in the boot archive, and
build; `std-test` is the example.

### POSIX tests

Each `.c` file in `userspace/posix` is built into
`/system/tests/posix`, and the runner, `run.c`, runs the tests its table
names in the `posix` boot test, each as a job of its own on a
pseudo-terminal. A test uses `check.h`'s `CHECK`, `CHECK_ERROR` and
`RUN`, prints `<name>: every check passed` and exits with how many
checks failed. Run them with:

```sh
./ob test boot --case posix
```

`libc:<name>` in the runner's arguments runs one of mlibc's own tests
with its output, for example
`./ob run --cmdline "-- --posix /system/tests/posix/run libc:ansi-snprintf"`,
and `libc-test:<name>` one of libc-test's, such as
`libc-test:functional-strtol`.
